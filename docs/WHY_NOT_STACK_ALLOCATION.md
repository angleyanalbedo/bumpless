# 深度技术规格书：为什么热更新状态实例绝不能选择栈分配？

> **核心结论**：在实时控制与热更新系统中，新结构体（新实例）的内存**绝不能分配在调用栈（Stack）上**，必须使用具备全局持久生命周期的**非实时后台堆分配（Non-RT Heap）**或**静态预分配双缓冲池（Static Arena）**。

本文从操作系统内存模型、实时系统确定性、生命周期逆转、跨线程安全及硬件级异常防护五个维度，系统性阐述不选择栈分配的根本技术原因。

## 一、 核心概念对比：栈 vs 堆 vs 静态区

在 C/C++ 与工控底层运行时的内存布局中：

```text
高地址  ┌────────────────────────────────────────────────┐
        │ 内核空间 (Kernel Space)                        │
        ├────────────────────────────────────────────────┤
        │ 调用栈 (Stack) ───向下增长──> [局部变量、函数栈帧]│ (临时、私有、自动回收)
        │                                                │
        │ 自由内存区 (Unallocated Memory)                 │
        │                                                │
        │ 堆区 (Heap)     ───向上增长──> [动态分配 malloc] │ (持久、跨函数、需显式管理)
        ├────────────────────────────────────────────────┤
        │ 静态数据区 (.bss / .data)      [全局变量、静态池] │ (与进程同生共死)
        ├────────────────────────────────────────────────┤
低地址  │ 代码段 (.text / .rodata)       [编译期只读指令]  │
        └────────────────────────────────────────────────┘
```

* **栈（Stack）**：后进先出（LIFO）。随函数调用指令（`call`/`push`）分配，随函数返回指令（`ret`/`pop`）自动作废。
* **堆（Heap）**：由系统内存分配器（如 `ptmalloc`, `jemalloc`）管理，生命周期跨越所有函数调用。
* **静态区（Static Data / Arena）**：在编译/链接期预分配固定物理区间，生命周期与系统运行周期完全一致。

## 二、 为什么绝不能选择栈分配？（五大致命原因）

### 1. 致命缺陷一：生命周期逆转与栈帧销毁 (Use-After-Free)

**这是否定栈分配最本质的物理法则。**

* **业务状态的本质**：
  工业功能块（FB）的结构体（如电机、PID 实例）属于**持久状态（Persistent State）**。电机的速度累加、编码器位置、PID 积分项必须在**几万甚至数亿个控制周期内持续存活**，直到下一次结构体变更或整机停机。
* **栈分配的执行流矛盾**：
  如果后台管理线程在准备新版本时，在局部函数（如 `bp_stage_func()`）的栈上定义或使用 `alloca()` 开辟了 `new_mem`：
  ```c
  void bp_stage_func(void) {
      FbMotor_V3 temp_stack_mem; // 分配在当前函数栈帧上！
      init_inst(&temp_stack_mem);
      // 试图将栈指针登记到全局实例槽位表
      g_inst_table[INST_MOTOR1] = &temp_stack_mem; 
  } // <--- 函数一旦退出，栈帧立即被销毁！
  ```
* **灾难后果**：
  `bp_stage_func` 执行完毕返回时，CPU 栈指针（ESP/RSP）复位。当下一微秒实时控制循环调用 `motor_exec()` 访问 `g_inst_table[INST_MOTOR1]` 时，**该地址早已失效，或者已被后续函数调用覆盖**。这将瞬间引发**栈踩踏（Stack Smashing）、内存随机污染，乃至操作系统的段错误（SIGSEGV / Access Violation）**。

---

### 2. 致命缺陷二：跨线程边界与线程私有栈冲突

在工业级高可用架构中，Bumpless 采用了**“后台管理线程准备 + 前台实时线程执行”**的双线程解耦模型：

```text
[非实时管理线程 (Non-RT Thread)]           [高优先级实时控制线程 (RT Thread)]
 优先级: 正常 (SCHED_OTHER)                优先级: 极高 (SCHED_FIFO 99)
 职责: 下载动态库、解析 Plan、准备新内存       职责: 微秒级周期中断、纯粹算法计算
        │                                         │
        ├──> 私有栈 A (Private Stack)              ├──> 私有栈 B (Private Stack)
```

1. **栈的私有性隔离**：
   在任何现代多任务 OS（Linux、Windows、QNX、VxWorks）中，**每个线程都有完全独立且私有的调用栈内存块**。线程私有栈通常由操作系统设置栈保护页（Stack Guard Page）。
2. **跨线程栈访问违规**：
   让实时线程去长期读写管理线程私有栈上的局部内存，不仅彻底打破了多线程隔离原则，而且一旦非实时线程处于休眠、被操作系统挂起甚至重新调度，实时线程对该栈的访问可能面临极高的**缓存伪共享（False Sharing）、TLB 抖动以及悬挂访问风险**。

---

### 3. 致命缺陷三：首周期故障回滚的双缓冲机制失效

Bumpless 的核心安全底线是：**热更新的新版本如果存在空指针、非法除零等致命缺陷，必须在首周期毫秒级自动回退到已知良好的旧版本。**

```text
             周期间隙切换时刻                     首周期验证结束
                    │                                    │
旧实例内存:  [保持在线 (存活)] ────────────────────────> [验证成功后才释放]
                    │                                    │
新实例内存:  [接管控制 (存活)] ────────────────────────> [转为正式主内存]
```

* **双缓冲必然要求同时驻留**：
  为了实现无感回滚，在第 1 个周期执行时，**新实例内存与旧实例内存必须在物理上同时有效共存**。如果新代码崩溃，系统能立即原子把指针恢复为旧实例。
* **栈无法提供确定性双缓冲**：
  栈内存具有严格的后进先出（LIFO）与不可倒序性，无法在跨周期的调度间隙中随意维持两份交替演进、条件释放的多版本实例映射。

---

### 4. 致命缺陷四：实时线程栈溢出（Stack Overflow）与确定性破坏

如果退一步退求其次，**“不让后台线程分配，让实时线程自己在循环入口栈上分配行不行？”** —— **同样绝对不行！**

1. **工控实时栈极度受限**：
   为了保证内存紧凑与确定性，在实时 Linux（PREEMPT_RT）或嵌入式 RTOS（FreeRTOS、Zephyr）中，实时控制线程的栈空间通常设置得极其紧凑（例如仅 **16 KB ～ 64 KB**，裸机上甚至只有 **4 KB**）。
2. **实例群规模无法预测**：
   一个复杂的 PLC 系统可能有上百个 FB（运动轴控制器、复杂滤波器、通信缓存区），单次热更涉及的实例总内存可能达到数十 KB 甚至数 MB。
3. **硬件级致命崩溃（HardFault）**：
   在实时线程栈上动态分配变长的新结构体实例（如使用 `alloca` 或 C99 VLA），极易在毫秒级周期间瞬时击穿栈保护页（Stack Guard），触发硬件级 `HardFault` 或内核 OOPS，导致整个控制器系统硬死锁。

---

### 5. 致命缺陷五：硬件级内存对齐与 DMA 传输限制

工控系统中的底层结构体通常需要与硬件协处理器（DSP、GPU）或总线（EtherCAT、CANopen、PCIe DMA）进行零拷贝映射：
* **对齐要求**：通常要求 8 字节、16 字节甚至 64 字节（CPU 缓存行 Cache Line）对齐以支持 SIMD 加速（AVX/NEON）或总线总线突发传输；
* **栈对齐的局限性**：动态栈分配（如 `alloca`）只能按照标准调用规约对齐（如 x86 4/8 字节），无法灵活保障大页（HugePage）物理连续性与严格的缓存行边界，易造成总线传输数据对齐异常（Alignment Fault）。

## 三、 工业级替代方案与最佳实践

基于以上技术限制，Bumpless 在架构中落地了两种工业级最佳实践方案：

### 方案 A：非实时后台线程堆分配（通用 OS 推荐）
* **分配方式**：在非实时管理线程中调用 `calloc(1, new_abi->inst_size)`。
* **为什么不破坏实时性？**
  * 传统系统忌讳 `malloc`/`calloc`，是因为堆锁（Heap Lock）、内存碎片、缺页异常（Page Fault）会导致毫秒级的时延抖动；
  * **Bumpless 实行计算前移**：所有的 `calloc`、缺页中断与构造函数执行，全部发生在**优先级很低的非实时后台线程**。无论堆分配花了 1 毫秒还是 10 毫秒，高优先级的实时控制线程都在照常运行，丝毫不受影响；
  * **实时周期间隙零分配**：在切换瞬间，实时线程只看到已经彻底分配并初始化完成的绝对物理指针，只跑纯 `memcpy`，**整个实时执行周期内完全不触碰堆分配器**。

---

### 方案 B：静态预分配双缓冲池（无堆 / MISRA-C / 严苛嵌入式推荐）
* **适用场景**：汽车电子（ISO 26262 / AUTOSAR）、轨道交通（EN 50128）、航空航天（DO-178C）等**完全禁用系统堆（Strictly No-Heap / MISRA-C）**的极严苛环境。
* **实现机制**：
  在编译链接期，直接在 `.bss` 全局数据段开辟静态双缓冲槽位池：
  ```c
  /* 全局静态预留池：零堆分配，零栈风险，生命周期永久 */
  static uint8_t g_inst_arena_A[BUMPLESS_MAX_INSTS][MAX_INST_SIZE];
  static uint8_t g_inst_arena_B[BUMPLESS_MAX_INSTS][MAX_INST_SIZE];
  ```
* **流转方式**：
  1. 当前运行使用 `Arena_A`；
  2. 后台准备 V3 时，指定备用的 `Arena_B` 对应槽位作为 `new_mem`；
  3. 周期间隙通过指针将槽位切换至 `Arena_B`；
  4. 既避免了栈的生命周期消亡与溢出风险，又彻底杜绝了动态堆的内存碎片问题。

## 四、 内存分配策略全景对比表

| 评估维度 | 栈分配 (Stack / alloca) | 非实时后台堆分配 (Non-RT Heap) | 静态双缓冲池 (Static Arena) |
| :--- | :--- | :--- | :--- |
| **内存生命周期** | ❌ **随函数返回立即销毁** | ✅ **跨周期永久存活** | ✅ **跨周期永久存活（与固件同生共死）** |
| **跨线程访问安全** | ❌ **私有栈冲突，高危悬挂** | ✅ **全局虚拟内存，线程安全** | ✅ **全局静态段，天然线程安全** |
| **实时线程确定性** | ❌ **引发栈溢出 (Stack Overflow)** | ✅ **零实时开销（后台承担分配）** | ✅ **100% 确定性（零分配）** |
| **首周期故障回滚** | ❌ **双缓冲无法跨栈保留** | ✅ **完美支持原子切回旧堆内存** | ✅ **完美支持双缓冲槽位秒级还原** |
| **内存占用开销** | 极低（但易爆栈） | 按需分配（高利用率） | 预先占用固定内存（需估算上限） |
| **无堆环境合规性** | ❌ 严苛工业标准不推荐 | ⚠️ 部分标准（MISRA-C）受限 | ✅ **100% 符合 MISRA-C / 航天标准** |
| **硬件/DMA 对齐** | ❌ 难以保障缓存行对齐 | ✅ 支持 `posix_memalign` / `_aligned_malloc` | ✅ 支持 `#pragma align` 编译期强制对齐 |

## 结论

在热更新引擎的设计中：
* **栈分配在系统原理和物理生命周期上完全不可行**，任何在栈上构造实例并传递给长期循环调度的做法，都会导致灾难性的内存段错误。
* Bumpless 采用的**“非实时后台堆分配”**（通用系统）与**“静态预分配双缓冲”**（严苛嵌入式系统），是保证**“持久生命周期、跨线程安全、确定性微秒级时延以及首周期无感回滚”**的唯一正确架构路线。
